# Этап «P0-харденинг перед запуском» — дизайн-документ

Дата: 2026-07-24
Статус: утверждён пользователем (по секциям в брейншторме)
Предшественники: `docs/plan-2026-07-20-hardening.md` (стадии A/B закрыты; этот документ — стадия «запуск»), техревью от 2026-07-24

## 1. Обзор

Четыре P0-блокера публичного запуска, закрываются одним этапом:

1. **TLS/WSS + деплой** — сейчас трафик и токены идут открытым текстом по `ws://`; деплой-конфигов в репо нет.
2. **Мультиаккаунт-фарм** — новый ник получает $500 стартового кэша, переводы без ограничений на личность: создал N ников → перевёл на основной.
3. **Расщепление на 101-м игроке** — `joinOrCreate('city')` создаёт вторую комнату со своим in-memory состоянием и вторым подключением к той же SQLite.
4. **Модерация** — нет ни кика/бана/мута, ни фильтра чата.

Рамки сохраняются: 100 игроков, тик 20 Гц, новых runtime-зависимостей не добавляем (подход A — «всё внутри сервера»).

## 2. Решения, принятые на брейншторме

| Вопрос | Решение |
|---|---|
| Инфраструктура | VPS и домена нет — готовим конфиги «под ключ» + инструкцию по покупке |
| TLS | Терминация на nginx (certbot/Let's Encrypt), сервер без изменений |
| Мультиаккаунт | Порог наигрыша 30 мин на переводы + суточный лимит переводов с одного IP |
| Модерация | Веб-панель админа (статика + HTTP API на существующем Express) + автоматика (фильтр мата, автомут за спам) |
| Одна комната | Сервер создаёт комнату сам при старте; клиент — `join`, переполнение → «Сервер полон» |

## 3. Константы (`shared/src/config.ts`)

```ts
export const TRANSFER_MIN_PLAYTIME_SEC = 1800;  // переводы после 30 мин наигрыша
export const TRANSFER_IP_DAILY_LIMIT = 1000;    // $ с одного IP за 24 ч
export const AUTOMUTE_VIOLATIONS = 5;           // срабатываний чат-кулдауна...
export const AUTOMUTE_WINDOW_MS = 60_000;       // ...за 60 сек...
export const AUTOMUTE_MINUTES = 10;             // ...→ автомут на 10 мин
```

## 4. TLS и деплой (`deploy/`, новый каталог)

- `deploy/nginx/mmo.conf` — виртуальный хост: TLS на 443 (терминация), прокси WebSocket на `127.0.0.1:2567` (`proxy_http_version 1.1`, `Upgrade`/`Connection` заголовки, `proxy_read_timeout 3600s`), статика клиента из `client/dist`, админка `/admin/` → `server/public/`, редирект 80→443.
- `deploy/systemd/mmo-server.service` — `ExecStart=npx tsx src/index.ts`, `Restart=always`, `EnvironmentFile=/etc/mmo/env` (вне репо: `PORT`, `GAME_DB`, `ADMIN_TOKEN`).
- `deploy/deploy.sh` — `git archive | ssh` → на сервере `npm ci --omit=dev`, сборка клиента (`npm run build -w client`), restart сервиса.
- `deploy/README.md` — пошагово: покупка VPS (мин. 1 vCPU / 1 GB), привязка домена (A-запись), `certbot --nginx`, генерация `ADMIN_TOKEN`.
- `client/src/net.ts` — если страница по `https`, URL по умолчанию `wss://${location.host}`; `VITE_SERVER_URL` остаётся для локальной разработки.
- `server/src/app.ts` — health-route `/healthz` → JSON `{status:"ok", players, uptimeSec}`; живого трафика не касаемся, без nginx всё работает по-прежнему на `ws://`.

Тест: интеграционный — `GET /healthz` отвечает 200 с полями. Клиентский URL — проверка руками (клиентских тестов нет, задача C1).

## 5. Мультиаккаунт-защита

**Данные:**

- `players` += `playtimeSec INTEGER NOT NULL DEFAULT 0` — идемпотентная миграция в `db.ts` (как существующие).
- Новая таблица `transfer_log (id INTEGER PK, fromName TEXT, toName TEXT, amount INTEGER, ip TEXT, ts INTEGER)` — строка на каждый успешный перевод.
- IP: из `req.headers['x-forwarded-for']` (первый адрес) с фолбэком на `req.socket.remoteAddress` — берётся в `onAuth`, живёт в памяти на клиенте комнаты, пишется в `transfer_log`.

**Правила перевода (`economy.ts`, до списания, отказы — существующим механизмом `transferResult`):**

1. `playtimeSec ≥ TRANSFER_MIN_PLAYTIME_SEC` у отправителя — иначе «Переводы доступны после 30 минут игры».
2. `SUM(amount)` по `transfer_log` за 24 ч с этого IP + новая сумма ≤ `TRANSFER_IP_DAILY_LIMIT` — иначе «Дневной лимит переводов с вашего IP исчерпан».
3. Существующие правила ($1–100k, rate-limit 500 мс) без изменений.

**Наигрыш:** тик комнаты раз в 60 сек всем онлайн-игрокам `+60` к `playtimeSec` в памяти; сброс в БД вместе с существующим 5-секундным сохранением (добавить поле). Зомби не считаются. AFK-накапливание приемлемо: 30 мин AFK ради $500 экономически бессмысленно.

Тесты (интеграционные, по образцу существующих): перевод до 30 мин → отказ; после (подкрутить `playtimeSec` напрямую в state) → успех; сумма с одного IP за сутки > лимита → отказ; старые записи (>24 ч) не учитываются.

## 6. Одна комната

- **Сервер:** после `gameServer.listen()` — `matchMaker.createRoom('city', {})`: единственная комната создаётся кодом сервера, а не по запросу клиента. В `CityRoom`: `autoDispose = false` (комната живёт вечно, переживает полный выход игроков), `maxClients = MAX_PLAYERS` (100, уже есть).
- **Клиент:** `joinOrCreate` → `join('city')` — присоединяется только к существующей, создать комнату клиент не может (это и есть гарантия синглтона). Ошибка переполнения/отсутствия комнаты → на экране входа локализованное «Сервер полон (100/100), попробуйте позже» — в существующий механизм ошибок входа.
- Реконнект (`allowReconnection(10s)`) не затрагивается.

Тесты (интеграционные): два клиента попадают в одинаковый `roomId`; комната не dispose-ится после выхода последнего клиента — следующий входит в ту же; при `maxClients=2` (опции комнаты в тесте) третий клиент получает отказ.

## 7. Модерация и админ-панель

**Данные (идемпотентные миграции в `db.ts`):**

```sql
bans  (name TEXT PK, ip TEXT, reason TEXT, until INTEGER, -- NULL = перманент
       byIp INTEGER NOT NULL DEFAULT 0, created INTEGER)
mutes (name TEXT PK, until INTEGER, reason TEXT)          -- мут всегда временный
```

**Принуждение:**

- `onAuth`: отказ при активном бане по нику, либо при бане с `byIp=1` и совпадении IP (галка «жёсткий бан по IP» — осознанный выбор, NAT бьёт по невинным). Сообщение: «Вы заблокированы до … / навсегда. Причина: …».
- `chat`/`sms`: активный мут по нику → отказ «Вы замьючены до …».

**HTTP API (`/admin/api/`, на существующем Express):**

- Авторизация: заголовок `Authorization: Bearer <ADMIN_TOKEN>` из env. Env не задан → все эндпоинты 503 (fail-closed); неверный токен → 401.
- `GET /state` — онлайн-игроки (ник, cash, wanted, playtimeSec, IP) + `{players, maxClients, uptimeSec}`.
- `POST /kick {name}` — найденному клиенту `leave()`; 404 если офлайн.
- `POST /ban {name, hours?, reason, byIp}` / `POST /unban {name}` — бан по нику, IP подхватывается из онлайна, если игрок на сервере.
- `POST /mute {name, minutes, reason}` / `POST /unmute {name}`.
- `GET /bans`, `GET /mutes` — списки с активностью.
- Доступ к комнате — модульный синглтон-реестр (`server/src/admin/registry.ts`), заполняется в `onCreate`, чистится в `onDispose`.

**Админ-страница `server/public/admin.html`:** ванильный JS без сборки. Поле токена (sessionStorage), таблица онлайн-игроков с кнопками kick / mute (минуты + причина) / ban (часы или перманент, причина, галка byIp), списки банов/мутов с кнопками снятия, автообновление 5 сек. В dev отдаётся `express.static('public')`, в prod — nginx по `/admin/`.

**Автоматика:**

- Фильтр мата: `shared/src/profanity.ts` — маленький словарь (RU+EN), функция `censor(text)` заменяет совпадения на `***`; применяется в обработчиках `chat` и `sms` (сообщение проходит, слово маскируется).
- Автомут за спам: существующий счётчик срабатываний чат-кулдауна расширяется — `AUTOMUTE_VIOLATIONS` нарушений за `AUTOMUTE_WINDOW_MS` → запись в `mutes` на `AUTOMUTE_MINUTES` мин с причиной «автомут: спам».

**Тесты:** бан блокирует вход (по нику; по IP при `byIp=1`; истёкший — нет), unban возвращает доступ; мут блокирует chat и sms; API: 503 без env-токена, 401 с неверным, kick дисконнектит клиента; `censor` маскирует (юнит); автомут после 5 нарушений кулдауна.

- Веб-админка с логином через Яндекс/CrazyGames SDK — будет частью портальной адаптации.
